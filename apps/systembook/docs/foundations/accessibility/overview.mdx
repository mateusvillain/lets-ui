## Commitment

Let's UI aims for **WCAG 2.2, level AA** conformance across all components and foundations. Level AA is the minimum: when an AAA criterion comes for free (such as body text contrast), the system meets it.

| Standard | Level | Scope |
| --- | --- | --- |
| WCAG 2.2 | AA | All components and foundations. |
| HTML | — | Semantic elements before ARIA. |
| WAI-ARIA 1.2 | — | Roles, properties and states, following the ARIA Authoring Practices patterns. |

Accessibility **is not a final step**: it is part of every component's definition of done. The full technical contract, per component, is in the repository's `A11Y.md` file; this page is the version for people who design and write.

<Callout variant="info">
  The system guarantees the accessibility **of the component**. The accessibility **of the screen** depends on how it is used: the label you write, the order in which you build the page, the color you pick for a chart. The content and testing sections below are for that.
</Callout>

## Principles

WCAG is organized into four principles. In Let's UI, each one becomes a practical question:

| Principle | The question | Example in the system |
| --- | --- | --- |
| **Perceivable** | Can the information be perceived through more than one sense? | Status with color **and** a label; images with alternative text. |
| **Operable** | Can everything be used with any form of input? | Every component works with the keyboard alone. |
| **Understandable** | Does the person understand what happened and what to do? | Error messages that say how to fix the problem. |
| **Robust** | Does it work with today's and tomorrow's assistive technologies? | Native HTML inside the Web Components; ARIA only where HTML is not enough. |

And three ideas that guide the decisions:

- **Native first.** A `<button>` is already focusable, announced and activated with `Enter` and `Space`. The system starts from the native element and only adds what is missing.
- **Never a single cue.** Color, shape, position and text reinforce each other. No information depends on a single sense.
- **Honesty about what is missing.** Debts are recorded and visible, on this page and on each component's page.

## What the system guarantees

### Contrast

| What | Minimum | Criterion |
| --- | --- | --- |
| Normal text on the background | **4.5 : 1** | 1.4.3 |
| Large text (from 24px, or 18.66px bold) | **3 : 1** | 1.4.3 |
| Control borders, icons that carry information, graphics | **3 : 1** | 1.4.11 |
| Focus ring against neighboring colors | **3 : 1** | 1.4.11, 2.4.7 |

The token pairs were measured in both themes, with the results in [Color](../properties/color.mdx). Body text and headings pass at **AAA**; the exceptions are in the debts below.

### Visible focus

- Every interactive element has a 3px **focus ring**, in the color of the component's family (WCAG 2.4.7).
- The ring appears with the keyboard (`:focus-visible`), not with a mouse click.
- Overlays that block the page trap focus while open and return it to the trigger when they close.
- Nothing fixed on the screen (header, toast) can hide the focused element (WCAG 2.4.11).

See the ring details in [Border](../properties/border.mdx).

### Keyboard

Everything you can do with the mouse is possible **with the keyboard alone** (WCAG 2.1.1), without focus traps (2.1.2). The patterns by component type:

| Component | Keys |
| --- | --- |
| [Button](../../components/actionable/button/index.mdx), [Link](../../components/navigation/link/index.mdx) | `Enter` activates; `Space` also activates the button. |
| [Checkbox](../../components/form-and-options/checkbox/index.mdx), [Switch](../../components/form-and-options/switch/index.mdx) | `Space` toggles. |
| [Radio Group](../../components/form-and-options/radio-group/index.mdx) | `Arrows` move and select; `Tab` enters and leaves the group. |
| [Tabs](../../components/navigation/tabs/index.mdx) | `Arrows` switch tabs; `Home` and `End` go to the first and the last. |
| [Accordion](../../components/content/accordion/index.mdx) | `Enter` and `Space` open; `Arrows` move between headers. |
| [Dropdown Menu](../../components/actionable/dropdown-menu/index.mdx) | `Arrows` navigate; `Esc` closes and returns focus to the trigger. |
| [Modal](../../components/content/modal/index.mdx), [Drawer](../../components/content/drawer/index.mdx) | `Esc` closes; focus stays trapped in the window. |

### Screen reader

- Every interactive element has its **role**, **name** and **state** announced correctly (WCAG 4.1.2).
- If there is visible text, it is the name. If there **is none** (an [Icon Button](../../components/actionable/icon-button/index.mdx)), `aria-label` is required.
- The accessible name **contains** the visible text, for people who use voice control (WCAG 2.5.3).
- Decorative icons and images are hidden from assistive technology.
- Form controls take part in the native form (`ElementInternals`) and expose validity, required state and error.

### Touch target

- Every interactive target is at least **24 × 24px**, or has free space around it that completes that area (WCAG 2.5.8).
- Primary controls use **40px**: Icon Button, Close Button, Avatar.
- Checkbox and Radio `md` have a 16px box and meet the minimum because the **label is part of the clickable area**. Do not use them without a label.

### Reduced motion

The system respects the operating system's **"reduce motion"** preference (`prefers-reduced-motion`). When it is on, height transitions, rotations and animated entrances are removed or replaced by a short fade. Accordion, Toast, Tooltip and Scroll Area already follow this rule; coverage for the rest is in the debts.

No animation in the system flashes more than three times per second (WCAG 2.3.1).

### Error and status messages

- On error, the field is marked as invalid (`aria-invalid`), the border changes **and** a text message appears, linked to the field by `aria-describedby` (WCAG 3.3.1).
- The message says **how to fix it**, not just what went wrong (WCAG 3.3.3). See [Writing](../content/writing.mdx).
- Required fields are announced as required (`aria-required`).
- Changes that happen without the person asking are announced by **live regions** (WCAG 4.1.3):

| Component | Announcement |
| --- | --- |
| [Alert](../../components/content/alert/index.mdx) | Assertive (`role="alert"`), in every variant: it interrupts reading. Reserve it for what needs immediate attention. |
| [Toast](../../components/content/toast/index.mdx) | Polite (`role="status"`): it waits for the current reading to finish. The error one is assertive and does not dismiss itself. |

## Content

The right component with the wrong content is still inaccessible. These rules belong to whoever writes and builds the screen.

### Heading hierarchy

- One `h1` per page, saying where the person is.
- Headings in order, without skipping levels (`h2` → `h3`, never `h2` → `h4`).
- The semantic level is chosen by structure, and the visual scale separately. See [Typography](../properties/typography.mdx).
- Use the `header`, `nav`, `main` and `footer` regions. Screen readers navigate by them.

### Alternative text

- An image that **informs**: describe what it communicates, not how it looks ("Chart: sales rose 20% in March").
- A **decorative** image: `alt=""`, so it is ignored.
- An image that is **the content of a link or button**: describe the destination or the action ("Go to home").
- Do not start with "Image of" — the screen reader already announces that it is an image.

### Descriptive links

- The link text says **where** it leads, even out of context: "View privacy policy", not "Click here".
- Links with the same text lead to the same destination.
- Warn when a link opens in a new tab or downloads a file.

### Plain language

- Short sentences, common words, active voice.
- One idea per sentence; one action per button.
- Declare the page language (`lang`) and that of passages in another language.
- The texts components generate on their own ("Close", "Show password") come in English and can be replaced through an attribute. Translate all of them.

## Non-visual states

Much of what the screen shows with color and shape needs to be stated in code for assistive technology.

| Attribute | For | Example |
| --- | --- | --- |
| `aria-label` | Naming an element **without visible text**. | Icon Button: `aria-label="Close"`. |
| `aria-labelledby` | Using text that is **already visible** as the name. Prefer it to `aria-label`. | A modal named by its title. |
| `aria-describedby` | Linking a complementary **description**: hint, error, tooltip. | A field with its error message. |
| `aria-invalid`, `aria-required` | Announcing error and required state. | Input with an error. |
| `aria-expanded`, `aria-selected`, `aria-checked` | Announcing open, selected and checked state. | Accordion, Tabs, Switch. |
| `aria-pressed` | Announcing whether a toggle button is on. | Filter or formatting Icon Button. |
| `aria-disabled` | Keeping an unavailable control announced. | Used together with `disabled`. |
| `aria-live`, `role="status"`, `role="alert"` | Announcing changes that happen on their own. | Alert, Toast. |
| `aria-hidden="true"` | Hiding what is decorative. Never on something focusable. | Icons next to text. |

<Callout variant="tip">
  Prefer not to disable. A disabled button does not explain why and drops out of keyboard navigation. It is often better to keep it active and show the error when the person tries to move forward.
</Callout>

### ARIA on the component element

A component's element (`<lui-button>`, `<lui-input>`) has no role of its own. An ARIA attribute left on it would make the browser show an extra node, without a role, next to the real control. That is why the component **consumes** the ARIA it accepts: it reads the attribute, carries the value to the inner control and removes it from the outer element.

This applies to Breadcrumb, Button, Card, Checkbox, Code Block, Icon Button, Input, Link, Radio, Select, Shortcut, Switch, Textarea and Tooltip. For developers:

- Attribute selectors (`lui-button[aria-expanded="true"]`) and `getAttribute('aria-*')` on the element no longer find the value. Read the property (`el.ariaExpanded`), or style from the owner of the state (`lui-modal[open]`).
- To clear a state, use an explicit value (`aria-expanded="false"`) or the property with `null`. Removing an attribute that has already been consumed has no effect. In frameworks, bind the property: `.ariaPressed=${pressed}` in Lit, `ariaPressed={pressed}` in React 19.
- `cloneNode()` and `outerHTML` do not carry the consumed ARIA. Set it again on the copy.
- Do not put an `aria-*` on the element that the component does not document.

## How to test

No single tool finds every problem. The system combines four layers, and a new screen should go through all of them:

| Layer | What it finds | How |
| --- | --- | --- |
| **Automation** | Contrast, missing names, invalid ARIA, structure. About a third of the problems. | axe-core in Storybook (A11y addon) and in the component tests. |
| **Keyboard** | Focus order, traps, invisible focus, unreachable actions. | Navigate with only `Tab`, `Shift+Tab`, `Arrows`, `Enter`, `Space` and `Esc`. |
| **Screen reader** | Names, roles, states and announcements that make no sense. | VoiceOver (macOS, iOS), NVDA (Windows), TalkBack (Android). |
| **Manual validation** | What depends on judgment: alternative text, clarity, hierarchy. | Review with the list below. |

### Checklist for each screen

1. **Keyboard**: can you do everything? Is focus always visible and does it follow the reading order?
2. **Screen reader**: do each control's role, name and state make sense? Are errors announced?
3. **Zoom**: with text at 200%, and at 320px wide, is the content still readable, without horizontal scrolling?
4. **Contrast**: do the new color pairs pass? In both themes?
5. **Without color**: in grayscale, is the information still understandable?
6. **Motion**: with "reduce motion" on, do the animations stop?
7. **High contrast**: with the system's forced colors, are boundaries and focus still visible?

## Exceptions and debts

The system records what does not yet meet the commitment, instead of hiding it. Each item has its impact and what to do until it is resolved.

| Debt | Criterion | Impact | Meanwhile |
| --- | --- | --- | --- |
| **White text on `caution`** in the light theme (3.83 : 1). | 1.4.3 | Filled tags and alerts. | Large text only; prefer the `surface` variant. |
| **Border of fields at rest** (`neutral.border.subtle`, 1.17 : 1). | 1.4.11 | Boundary of Input, Select and Textarea. | Label always visible; field on the neutral surface. |
| **Reduced motion** does not yet cover the Button spinner, state transitions and the entrances of Dropdown Menu and Modal. | 2.3.3 | Animations keep running with the preference on. | Avoid custom animations without `prefers-reduced-motion`. |
| **Avatar status indicator** below 3 : 1 against the ring. | 1.4.11 | Status perceived by shape only. | See [Avatar](../../components/content/avatar/accessibility.mdx). |
| **Automation does not block.** Storybook's A11y addon runs in warning mode, not error mode. | — | Regressions can slip through without breaking the build. | Review the A11y panel of every changed story. |

<Callout variant="warning">
  A new exception goes into this table **before** the component is published, with the criterion, the impact and the interim guidance. An unrecorded debt is a hidden debt.
</Callout>
