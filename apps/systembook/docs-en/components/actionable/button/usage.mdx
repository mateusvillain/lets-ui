## Action hierarchy

The screen should make the next step clear at a glance. That is the hierarchy: **one primary action**, as many secondary ones as needed and, at most, one destructive action at a time.

<DosDonts variant="do" title="One primary action per context">
  Pair a Primary button with a Secondary one. The person immediately sees which path is recommended and which is the way out.
</DosDonts>

<DosDonts variant="dont" title="Several primary actions side by side">
  Two buttons with the same weight compete for attention, and no one knows which is the main one. Demote one of them to Secondary or Neutral.
</DosDonts>

## Position and order

- In forms and dialogs, align the buttons to the **end** of the content (to the right in left-to-right languages).
- Place the primary action **last** in reading order, after the secondary one: "Cancel" and then "Save".
- On small screens, stack the buttons with `block` and keep the primary action at the top.
- Keep 8px or 16px of space between buttons in the same group, never buttons stuck together.

## Writing the label

The label is a **verb in the imperative** that says what will happen.

<DosDonts variant="do" title="Verb + object">
  "Save changes", "Delete project", "Send invite". The person knows the result before clicking.
</DosDonts>

<DosDonts variant="dont" title="Generic labels">
  "OK", "Yes", "Send" with no context, or "Click here". They force the person to reread the question to understand the effect.
</DosDonts>

More guidance:

- Use up to **three words** and sentence case ("Create account", not "Create Account").
- Do not use final punctuation.
- In destructive actions, name what will be lost: "Delete 3 files" is better than "Delete".
- Use the same verb for the same action across the whole product.

## Destructive actions

Use `danger` only when the action **cannot be undone** or causes data loss. For reversible actions, prefer offering "Undo" afterwards instead of asking for confirmation first.

<Callout variant="warning">
  When the action is irreversible, confirm it in a [Modal](../../content/modal/index.mdx), naming what will be deleted. The confirmation button repeats the verb: "Delete project".
</Callout>

## Loading

When starting an operation that takes more than a moment, turn on `loading`. The button keeps its size, shows progress and blocks repeated clicks, avoiding duplicate submissions.

- Change the label with `loading-text` when it helps: "Saving…".
- Do not disable the button to indicate loading. Disabled means "unavailable", not "in progress".

## Disabled button

Use `disabled` sparingly. A disabled button does not explain why it is unavailable.

- Prefer keeping the button active and showing the validation error when the person tries to move forward.
- If disabling is necessary, explain the reason in nearby text or in a [Tooltip](../../content/tooltip/index.mdx).

## Best practices

- A button **does something**; if it takes you somewhere else, use a link.
- Give the button a touch target of at least 40px on touch screens, which is `lg`.
- Do not use two different styles for the same action on different screens.
- Do not add icons just for decoration. If the icon adds no meaning, leave the text alone.
