# File Upload

Field for attaching files to a form. It combines a drop zone (drag-and-drop) with a button that opens the native picker, lists the chosen files with name and size, validates type, size and count locally, and lets each file be removed.

The component **does not send** files: the app makes the request and reports each one's progress with `setFileStatus()`. The field shows progress, failure and the retry button in the same list. See [Sending](#sending-progress-failure-and-retry).

## Quando usar

Use o File Upload quando a pessoa precisa anexar um ou mais arquivos do próprio dispositivo: um comprovante, um currículo, as imagens de um anúncio.

- Para um único arquivo num formulário curto, sem lista nem arrastar e soltar, um `<input type="file">` nativo pode bastar (veja [Classe CSS](#classe-css-sem-web-component) para estilizá-lo).
- Para escolher entre arquivos que já estão no sistema (uma biblioteca de mídia, documentos já enviados), use uma lista ou um [Native Select](?path=/docs/form-and-options-native-select--docs), não o seletor do dispositivo.
- Para texto colado ou digitado, use o [Textarea](?path=/docs/form-and-options-textarea--docs).

<Lang lang="en-US">
## When to use

Use File Upload when the person needs to attach one or more files from their own device: a receipt, a résumé, the pictures of a listing.

- For a single file in a short form, with no list and no drag-and-drop, a native `<input type="file">` may be enough (see [CSS class](#css-class-without-web-component) to style it).
- To choose among files already in the system (a media library, documents already sent), use a list or a [Native Select](?path=/docs/form-and-options-native-select--docs), not the device picker.
- For pasted or typed text, use [Textarea](?path=/docs/form-and-options-textarea--docs).

## Vários arquivos

Com `multiple`, cada nova seleção **soma** aos arquivos já presentes, até `max-files`. Sem `multiple`, um arquivo válido **substitui** o atual.

- **Duplicatas:** um arquivo idêntico a um da lista (nome, tamanho, tipo e data de modificação) é ignorado e anunciado como “already in the list”.
- **Seletor cancelado:** fechar o seletor do sistema sem escolher nada não altera a lista.
- **Nomes longos** quebram linha em qualquer ponto em vez de serem truncados, para continuarem identificáveis em telas pequenas e com zoom.

</Lang>

<Lang lang="en-US">
## Multiple files

With `multiple`, each new selection is **added** to the files already there, up to `max-files`. Without `multiple`, a valid file **replaces** the current one.

- **Duplicates:** a file identical to one in the list (name, size, type and last-modified date) is skipped and announced as “already in the list”.
- **Cancelled picker:** closing the system picker without choosing leaves the list unchanged.
- **Long names** wrap at any point instead of being truncated, so they stay identifiable on small screens and under zoom.

</Lang>

<Lang lang="pt-BR">
## Validação local

Cada arquivo é validado sozinho contra `accept`, `max-size` (bytes, por arquivo) e `max-files`. Um arquivo inválido **não derruba os válidos**: ele aparece na lista com borda de erro e uma mensagem que diz **qual arquivo**, **o problema** e **como resolver**, e não entra no `FormData` nem em `files`. Sai com o botão Remover ou na próxima seleção. Para cada recusa o componente emite `lui-error`.

`accept` também filtra o seletor do sistema, mas **não substitui a validação no servidor**: tipo (pelo conteúdo, não só pela extensão), tamanho, quantidade e conteúdo precisam ser verificados de novo no backend, pois o navegador aceita o que a pessoa renomear.

</Lang>

<Lang lang="en-US">
## Local validation

Each file is validated on its own against `accept`, `max-size` (bytes, per file) and `max-files`. An invalid file **does not drop the valid ones**: it appears in the list with an error border and a message that names **the file**, **the problem** and **how to fix it**, and it is not in `FormData` or `files`. It leaves with its Remove button or on the next selection. For each rejection the component emits `lui-error`.

`accept` also filters the system picker, but it **does not replace server-side validation**: type (by content, not just extension), size, count and content must be checked again on the backend, since the browser accepts whatever the person renames.

## Envio: progresso, falha e nova tentativa

A aplicação envia; o campo mostra. Ela pega os arquivos em `files` (ou em `lui-change`), faz a requisição e chama `setFileStatus()` a cada mudança:

| Status      | Opções         | Na tela                                                                  |
| ----------- | -------------- | ------------------------------------------------------------------------ |
| `selected`  | —              | Estado inicial de um arquivo aceito.                                     |
| `uploading` | `{ progress }` | Barra de progresso com porcentagem. Sem `progress`, barra indeterminada. |
| `complete`  | —              | Igual a `selected`, como no protótipo; o estado vai em texto oculto.     |
| `error`     | `{ message }`  | Borda de erro, ícone, mensagem e botão **Retry**, que emite `lui-retry`. |

</Lang>

<Lang lang="en-US">
## Sending: progress, failure and retry

The app sends; the field shows it. It takes the files from `files` (or from `lui-change`), makes the request and calls `setFileStatus()` on every change:

| Status      | Options        | On screen                                                                  |
| ----------- | -------------- | -------------------------------------------------------------------------- |
| `selected`  | —              | Initial state of an accepted file.                                         |
| `uploading` | `{ progress }` | Progress bar with percentage. Without `progress`, an indeterminate bar.    |
| `complete`  | —              | Same as `selected`, as in the prototype; the state goes in hidden text.    |
| `error`     | `{ message }`  | Error border, icon, message and a **Retry** button that emits `lui-retry`. |

</Lang>

<Canvas of={FileUploadStories.UploadStates} />

```js
const field = document.querySelector('lui-file-upload');

async function upload(file) {
  field.setFileStatus(file, 'uploading', { progress: 0 });
  try {
    await send(file, (progress) =>
      field.setFileStatus(file, 'uploading', { progress })
    );
    field.setFileStatus(file, 'complete');
  } catch {
    field.setFileStatus(file, 'error', {
      message: 'Failed. Check your connection and retry.',
    });
  }
}

field.addEventListener('lui-retry', (e) => upload(e.detail.file));
```

<Lang lang="en-US">
## Events `lui-change` and `lui-error`

`lui-change` is emitted when accepted files come in or go out, with `files` (the whole list), `added` and `removed` in `event.detail`. `lui-error` is emitted once for each rejected file, with `file`, `reason` (`'type'`, `'size'` or `'count'`) and `message`. ## Acessibilidade

- A área inteira é um `<button>` nativo nomeado pelo título (`label`): `Tab` chega nela e `Enter`, `Espaço` ou toque abrem o seletor. Descrição, restrições, “Required.” (com `required`) e a mensagem de erro ficam ligados a ela por `aria-describedby`.
- A lista é um `<ul>` rotulado (“Selected files”); cada item expõe nome, tamanho e, quando houver, a mensagem de erro ou a barra de progresso.
- `Tab` e `Shift+Tab` percorrem a área e os botões de **cada** arquivo. Remover e Retry são botões distintos, com o nome do arquivo no nome acessível (“Remove comprovante.pdf”, “Retry comprovante.pdf”).
- Depois de remover, o foco vai para o Remover do arquivo que tomou o lugar, senão o anterior, senão a área. Depois de Retry, quando a aplicação volta o arquivo para `uploading`, o foco vai para o Remover do mesmo arquivo, nunca para um elemento que sumiu.
- Cada barra de progresso é um `role="progressbar"` com o nome do arquivo (“Uploading comprovante.pdf”).
- Adições, recusas, remoções e mudanças de status (início, envio concluído, falha) são anunciadas numa região `role="status"` educada, sem mover o foco. Os passos do progresso **não** são anunciados.
- O ícone de erro é decorativo; a mensagem é texto. O foco da área aparece também em modo de alto contraste (`forced-colors`).

### Responsabilidades de quem usa

- Informe o envio com `setFileStatus()`. Sem isso, o arquivo fica como selecionado para sempre e quem usa leitor de tela não sabe se ele foi enviado.
- Escreva mensagens de falha que digam o que fazer (“Check your connection and retry”), não só “Failed”.
- Defina e diga quando o envio acontece: ao escolher ou por um botão de envio. Se for ao escolher, diga isso no `description`.
- Ao remover um arquivo em envio, cancele a requisição dele (ele vem em `removed` no `lui-change`).
- Revalide tipo, tamanho, quantidade e conteúdo no servidor.
- Não prometa retomar envio interrompido nem manter arquivos depois de recarregar a página, a menos que o backend realmente suporte isso.

## Accessibility

- The whole zone is a native `<button>` named by the title (`label`): `Tab` reaches it and `Enter`, `Space` or touch open the picker. Description, constraints, “Required.” (with `required`) and the error message are tied to it through `aria-describedby`.
- The list is a labelled `<ul>` (“Selected files”); each item exposes name, size and, when present, the error message or the progress bar.
- `Tab` and `Shift+Tab` move through the zone and the buttons of **each** file. Remove and Retry are distinct buttons, carrying the file name in their accessible name (“Remove receipt.pdf”, “Retry receipt.pdf”).
- After a removal, focus goes to the Remove button of the file that took its place, else the previous one, else the zone. After Retry, when the app sets the file back to `uploading`, focus goes to the same file's Remove, never to an element that is gone.
- Each progress bar is a `role="progressbar"` named after the file (“Uploading receipt.pdf”).
- Additions, rejections, removals and status changes (start, sent, failed) are announced in a polite `role="status"` region, without moving focus. Progress ticks are **not** announced.
- The error icon is decorative; the message is text. The zone's focus also shows in high contrast mode (`forced-colors`).

### Consumer responsibilities

- Report sending with `setFileStatus()`. Without it, the file stays selected forever and screen reader users cannot tell whether it was sent.
- Write failure messages that say what to do (“Check your connection and retry”), not just “Failed”.
- Decide and say when sending happens: on selection or through a send button. If on selection, say so in `description`.
- When a file is removed while sending, cancel its request (it comes in `removed` on `lui-change`).
- Re-check type, size, count and content on the server.
- Do not promise resuming an interrupted upload or keeping files after a reload unless the backend really supports it.

</Lang>
